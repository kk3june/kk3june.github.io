## 들어가며

빌드가 통과했다. 테스트도 초록불이다. 그런데 그게 `package.json`에 적힌 선언이 전부 옳다는 뜻일까? 아니다. 안 쓰는데 선언돼 있거나, 잘못 선언됐는데도 우연히 굴러가는 패키지는 에러도 안 내고 빌드도 멀쩡히 통과한다. 그래서 아무도 의심하지 않고, 몇 번의 리팩터를 거치고도 그대로 남는다.

[1편](/blog/pnpm-monorepo-dependency-cleanup/)에서는 의존성을 **어디에 선언하고 어떤 버전으로 고정할지**를 정리했다. 이번 글은 그다음 문제다. 선언된 패키지와 **실제 사용이 맞지 않는** 경우.

이 글은 그렇게 빌드 뒤에 조용히 남아 있던 의존성들을 추적한 기록이다. 사례는 크게 네 가지 패턴으로 묶였고, 거기에 어느 패턴에도 안 들어가는 게 하나 더 있었다. 환경은 pnpm 모노레포지만, 방법 자체는 패키지 매니저와 무관하다.

## 비대칭은 단서일 뿐, 근거는 전수 검증

`package.json`에 적힌 선언 한 줄은 **"이 패키지가 여기서 쓰인다"는 주장**이다. 그리고 앞서 말했듯, 빌드는 그 주장을 검증해주지 않는다. 그러니 선언된 패키지가 실제로 쓰이는지는 빌드와 별개로 따로 확인해야 한다. 문제는 "어떻게"다.

가장 손쉬운 방법은 `pnpm dlx knip` 같은 도구로 안 쓰는 패키지를 리스트업한 뒤 하나씩 지워나가는 것이다. 모노레포라면 앱 간 비대칭을 단서로 삼는 방법도 있다. 실제로 이 작업도 그렇게 시작했다. 직전에 누군가 의존성 정리를 했는데, `react-pdf`와 `react-sortablejs`를 **A 앱에선 지웠고 B·C 앱에선 안 지웠다.** 같은 패키지가 앱마다 다르게 처리돼 있으니 눈길이 갔다.

하지만 비대칭은 단서로 삼기엔 약하다. 모노레포에서 앱마다 의존성이 다른 건 **당연하기 때문**이다. 한 앱엔 차트 라이브러리가 있고 다른 앱엔 없을 수 있고, 그건 각 앱이 실제로 쓰는 게 달라서다. 그러니 "목록이 다르다"는 것 자체는 신호가 아니다. 의미가 있으려면 **사용은 같은데 선언만 다른** 경우여야 한다 — 사용 차이로 설명되지 않는 선언이니까. 비대칭이 잡아주는 건 딱 거기까지다.

게다가 이번에 그게 그나마 통한 것도 **특수한 조건 덕**이었다. 세 앱은 같은 `packages/components`를 공유하는 사실상 형제 앱이라, PDF 같은 공통 기능에 대해선 의존성이 대체로 일치해야 한다. 그래서 "공통 기능인데 선언만 엇갈린" 게 눈에 띈 것이다. 앱들이 서로 다른 도메인을 다루는 일반적인 모노레포였다면 — 마케팅 사이트와 관리자 대시보드처럼 — 의존성이 제각각인 게 기본값이라 비대칭은 아무 신호도 주지 못한다. 즉 비대칭이 단서가 된 건 이 레포의 우연한 특성이지, 일반화할 수 있는 방법이 아니다.

그리고 비대칭에 기대면 놓치는 게 생긴다. 뒤에 나올 `react-transition-group`은 **세 앱 모두에서** 미사용이라 완벽히 대칭이었다. 비대칭만 좇았다면 영영 못 잡았을 케이스다. 결국 비대칭은 "어디부터 볼까"를 정해주는 싸구려 힌트일 뿐, 판정의 근거는 아니다. 근거는 전수 검증이다. 아래 사례들은 그 전수 검증에서 걸린 것들이고, 네 가지 패턴으로 묶였다 — 그리고 마지막에 어디에도 안 묶이는 하나가 더 있다.

## 빌드는 통과한 의존성 문제들

전수 검증에서 걸린 것들을 패턴별로 본다. 도구가 문자열에 속은 것, 사람이 아예 안 본 것, 비슷한 이름에 낚인 것 — 살아남은 사연이 제각각이다. 마지막엔 어느 패턴에도 안 묶이는 예외 하나가 붙는다.

### 패턴 A — 문자열 오탐 (`react-pdf`)

`react-pdf`부터 봤다. B·C 앱에서 grep하니 `import`는 한 줄도 없고 각 앱에서 이것만 잡혔다.

```ts
const PdfWrap = styled.div`
  .react-pdf__Document {
    display: flex;
    justify-content: center;
  }
`;
```

styled-components 안의 CSS 클래스 셀렉터일 뿐, 패키지 import가 아니다. 사실 **세 앱 어디도 `react-pdf`를 직접 import하지 않는다.** PDF 미리보기는 전부 `packages/components`의 `PDFViewer`/`FilePreview`를 가져다 쓰고, `react-pdf`를 실제로 import하는 건 그 components 하나뿐이다. A 앱도 PDF 화면이 있지만 마찬가지로 components 경유다. 즉 **세 앱은 react-pdf에 대해 같은 처지** — 아무도 직접 안 쓰고, 따라서 아무도 직접 선언할 필요가 없다. 그런데 B·C 앱만 선언을 달고 있었다.

CSS 셀렉터 한 줄이 왜 중요하냐면, **substring 기반 도구를 속이기 때문**이다. depcheck처럼 "파일에 `react-pdf`라는 문자열이 있으면 사용 중"으로 보는 도구는 이 `.react-pdf__Document`를 사용으로 오판한다. 하필 `{패키지명}__{요소}`는 흔한 CSS 네이밍 컨벤션이라 오탐이 자연스럽게 만들어진다. 직전 작업이 B·C 앱은 남기고 A 앱만 지운 것도, 이 substring 오탐으로 설명된다 — 셀렉터가 있는 B·C 앱은 "사용 중"으로 보였고, 셀렉터가 없는 A 앱은 "미사용"으로 보였을 것이다.

대응은 둘 중 하나다. AST 기반 도구를 쓰거나, grep을 쓰더라도 import 구문으로 범위를 좁힌다.

```bash
grep -rEn "from ['\"]react-pdf['\"]|require\(['\"]react-pdf['\"]\)" <app>/src
```

실제로 AST 도구(knip)를 돌려보니 CSS 셀렉터에 안 속고 B·C 앱의 react-pdf를 정확히 "미사용"으로 잡았다. 여기까진 AST가 substring을 이긴다.

다만 한 가지 더. knip이 답하는 질문은 **"선언했는데 안 쓰는 게 뭐냐"**다. 그래서 A 앱은 출력에 아예 안 나온다 — 미사용이라서가 아니라 **선언 자체가 없어서 검사 대상이 아니라서**다. 이 침묵을 "A 앱은 react-pdf를 잘 쓰는 중"으로 읽으면 곤란하다. A 앱도 B·C 앱과 똑같이 직접 안 쓰는데, 선언이 없어 레이더에 안 잡힐 뿐이다. 도구는 "선언된 것"만 말한다. 세 앱이 같은 처지라는 결론은 도구 출력만으로는 안 나오고, 결국 사람이 교차해 읽어야 한다. 비대칭을 만든 게 substring이든 "선언 여부"든, **도구를 바꾼다고 비대칭이 사라지는 게 아니라 원인이 옮겨갈 뿐**이다.

참고로 `react-pdf`는 `packages/components`가 직접 선언해 쓰고 있어서, 앱에서 중복 선언을 지워도 컴포넌트를 통해 transitive로 정상 동작한다.

### 패턴 B — transitive 회색지대 (`react-sortablejs`)

`B 앱`은 `react-sortablejs`를 직접 import하지 않는다. 대신 `packages/components`의 정렬 컴포넌트를 transitive로 폭넓게 쓴다. 아마 직전에 정리한 사람은 "직접 import는 없어도 컴포넌트를 통해 쓰이니 일단 남겨두자"고 판단했을 것이다. 문제는 `C 앱`에는 직접 import가 있어 자연히 남았고, `B 앱`만 애매한 채로 남았다는 점이다.

이런 회색지대를 없애려면 정책을 둘 중 하나로 못 박아야 한다.

- 축 A (strict): 직접 import 없으면 선언하지 않는다 → 일관 제거
- 축 B (safe): transitive로라도 쓰이면 명시적으로 선언한다 → 일관 유지

둘 다 일리가 있다. 틀린 건 케이스마다 다르게 적용하는 거다. 이 프로젝트는 1편에서부터 hoist 안티패턴 해소(strict)를 지향했으니 축 A에 가깝고, 그렇다면 `B 앱`의 `react-sortablejs`도 같이 지워졌어야 했다.

### 패턴 C — 검사 목록의 사각지대 (`react-transition-group`)

가장 명백한 케이스가 가장 늦게 발견됐다. `react-transition-group`은 모노레포 전체 grep 결과가 **0건**이었다. `TransitionGroup`, `CSSTransition`, 패키지명까지 전부 0건. 그런데도 세 앱 모두에 선언돼 있었다.

여기서 앞의 "비대칭" 얘기로 돌아가 보자. 이 패키지는 세 앱에 똑같이 선언돼 있고 똑같이 안 쓰인다. **완벽히 대칭**이다. 비대칭을 단서로 삼는 방법이었다면 **이건 영영 못 잡는다.** 엇갈린 게 없으니 눈에 걸릴 것도 없다. 그런데도 잡혔다 — 비대칭을 좇아서가 아니라, 선언을 하나씩 전수로 대조했기 때문이다. 이 케이스가 "비대칭은 방법이 아니다"라는 증거다.

못 잡은 이유도 같은 결이다. 직전 작업은 "루트에서 옮길 패키지 목록을 정해 처리"하는 방식이었고, 그 목록 밖의 후보는 애초에 시야에 들어오지 않았다. 도구의 한계가 아니라 절차의 한계다. 어떤 정적 분석 도구를 돌렸어도 0건짜리는 잡았을 텐데, 돌리지 않은 게 문제였다. 그래서 이런 작업의 첫 단계는 "주어진 목록을 처리"가 아니라 **"전수 조사로 목록을 만든다"**가 돼야 한다.

### 패턴 D — 묶음 추측 (`ckeditor5`, `redux`)

`packages/components`는 ckeditor 관련 패키지를 세 개 선언하고 있었다.

```json
"@ckeditor/ckeditor5-build-classic": "40.2.0",  // 실제 import
"@ckeditor/ckeditor5-react": "6.3.0",           // 실제 import
"ckeditor5": "40.2.0"                           // 우연히 같이 보임
```

코드는 `@ckeditor/*` 서브패키지만 import한다. umbrella 격인 `ckeditor5`는 어디서도 import되지 않고, peer로 요구되지도 않으며(요구되는 건 전부 `@ckeditor/ckeditor5-*` 서브패키지다), 다른 ckeditor 패키지의 dependency도 아니다. 그냥 잘못 선언된 흔적이다.

왜 살아남았을까. 세 패키지 이름이 비슷해서다. 셋이 한 묶음이니 다 필요하겠거니 하는 추측이 작동한 거다. `redux`도 비슷하다. `@reduxjs/toolkit`이 `redux`의 핵심 API를 그대로 re-export하기 때문에 `import { combineReducers } from '@reduxjs/toolkit'`이면 충분한데, "redux 3종 세트"라는 관습이 `redux` 직접 선언을 남겨뒀다.

물론 umbrella가 다 불필요한 건 아니라서 함정이다. `rxjs`나 `@mui/material`은 umbrella 자체가 필수다. 그러니 이름만 보고 판단하지 말고 peer-dep과 실제 import 양쪽으로 확인해야 한다.


| umbrella 이름     | 실제 import 대상                 | 판정              |
| --------------- | ---------------------------- | --------------- |
| `ckeditor5`     | `@ckeditor/ckeditor5-*`      | umbrella 거의 불필요 |
| `redux`         | `@reduxjs/toolkit` re-export | 직접 선언 불필요       |
| `rxjs`          | `rxjs/operators` 등           | umbrella 필수     |
| `@mui/material` | 동일                           | umbrella 필수     |


### 예외 — 빌드·런타임 괴리 (`pdfjs-dist`)

마지막 하나는 성격이 좀 다르다. `pdfjs-dist`는 `vite.config.ts`에서 `require.resolve`로 cmap 파일을 빌드 산출물에 복사하고 있었다. 그래서 정적 분석상으로는 "사용 중"이 맞다. 오탐이 아니다. 그런데 런타임은 그 복사된 파일을 쓰지 않았다. 런타임 코드는 cMap을 unpkg CDN에서 받고 있었다.

정리하면 이런 상태였다.

- 빌드할 때마다 169개 `.bcmap` 파일이 dist에 복사됨 × 2개 앱 = **338개의 안 쓰는 에셋 (약 3.2MB)**
- 빌드용 `pdfjs-dist`(4.4.168)와 런타임 CDN 버전(4.8.69)이 서로 다른 버전
- 동시 설치 버전 2개에, `vite-plugin-static-copy`의 unmet peer 경고까지 따라붙음

빌드 설정의 의도와 런타임 동작이 어긋나 있었던 거다. 런타임이 이미 CDN을 쓰고 있으니 `pdfjs-dist` 직접 선언과 cmap static-copy를 걷어내도 동작은 그대로다. 대신 안 쓰는 에셋 338개가 사라지고, 동시 설치 버전이 1개로 합쳐지고, peer 경고도 같이 정리됐다. **정적 분석이 "사용 중"이라고 해도, 그 사용이 런타임까지 닿는지는 또 다른 문제다.**

비슷한 결로, `date-fns/locale`에서 `da`(덴마크어 로케일)를 import해놓고 한 번도 쓰지 않던 죽은 import도 하나 있었다. 이런 건 패턴이라기보다 그냥 지우면 되는 부스러기지만, 전수 조사를 안 하면 똑같이 남는다.

## 한 도구를 믿지 않는다 — 여러 툴로 교차검증

그래서 어떻게 검출하느냐. 이 사례들을 겪고 나서 정리한 절차는 이렇다. 핵심은 하나다 — **도구 하나를 믿지 않는 것**.


| 도구                | 강점              | 한계                                            |
| ----------------- | --------------- | --------------------------------------------- |
| `depcheck`        | 빠름              | substring 오탐 (패턴 A)                           |
| `knip`            | AST 기반, 모노레포 인식 | "선언된 것"만 검사 → 선언 안 한 transitive 사용엔 침묵 (패턴 A) |
| grep              | 즉시 확인           | import 구문으로 범위를 좁혀야 함                         |
| `tsc` + import 추적 | 가장 정확           | 손이 많이 감                                       |


의존성을 건드리는 작업마다 이 순서를 따른다.

1. **검출(전수 조사)** — `knip` 또는 `depcheck`로 워크스페이스 단위 후보를 뽑는다. "목록을 처리"하지 말고 "목록을 생성"하는 데서 시작한다. (패턴 C 방지)
2. **분류** — 후보를 아래 4분면에 넣는다.

  |                 | 코드 import 있음 | 코드 import 없음             |
  | --------------- | ------------ | ------------------------ |
  | **빌드 설정 사용 있음** | 정상           | 유지 (예: vite.config의 빌드툴) |
  | **빌드 설정 사용 없음** | 정상           | 제거 후보                    |

3. **peer-dep 반증** — 제거 후보가 다른 선언 패키지의 peer로 요구되는지 확인한다. (패턴 D 방지)
4. **transitive 검증** — 다른 워크스페이스 경유로 닿는지 확인하고, 정책 축(A/B)을 일관되게 적용한다. (패턴 B 방지)
5. **빌드 + 런타임 검증** — `pnpm install && pnpm -F <ws> build && pnpm -F <ws> dev`로 prod·dev 양쪽을 본다. 정적 분석이 "사용 중"이라 해도 런타임에 닿는지는 별개다. (`pdfjs-dist` 케이스 방지)

`depcheck`는 빠른 대신 substring 오탐이 있고(패턴 A), `knip`은 AST 기반이라 그 오탐은 피하지만 "선언된 것"만 검사해서 선언 안 한 transitive 사용은 침묵으로 넘긴다(패턴 A 후반부). 그래서 최소 두 도구를 교차해서 보고, peer-dep과 build-config 사용 여부는 손으로 확인하는 게 안전하다.

## 마치며

1편의 결론이 "선언을 어디에 어떻게 둘 것인가"였다면, 2편의 결론은 한 줄 더 붙는다. **그 선언이 실제 사용과 맞는지는 따로 확인해야 한다.** 빌드 통과는 그걸 보장하지 않는다.

이 사례들을 관통하는 공통점은, 전부 "조용히" 통과했다는 거다. 충돌이 나서 막혔다면 진작 고쳤을 텐데, 빌드가 멀쩡하니 아무도 의심하지 않았다. 그리고 직전 작업자가 이걸 놓친 건 실력이 부족해서가 아니라 "주어진 목록만 처리"하는 절차 때문이었다. 즉 이건 능력의 문제가 아니라 **절차의 문제**다.

그래서 남길 건 걷어낸 패키지 목록이 아니라 방법이다. 비대칭이든 도구 출력이든 그럴듯한 힌트에 기대지 말 것 — 그건 어디부터 볼지 정해줄 뿐, 대칭으로 숨은 건 못 잡는다. 대신 **선언을 하나씩 실제 사용에 대조하는 전수 검증**을 한 번 만들어 두고, 다음 사람이 그대로 밟을 수 있게 남겨두는 것. 의존성 관리에서 오래 가는 건 결국 이거라고 생각한다.
