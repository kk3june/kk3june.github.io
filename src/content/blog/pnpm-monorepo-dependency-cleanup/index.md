# 들어가며

회사에서 모노레포 환경의 레거시 프로젝트의 개선 작업을 담당하게 되었다. 해당 프로젝트는 모노레포로 개발환경이 세팅되었지만, 일정 상의 문제로 사전에 디테일한 업무 협의가 이루어지지 않은 채 개발이 수 년간 진행되었고 그 결과 각 애플리케이션 별로 버전이 크게 상이한 부분이 많았다. 최근 버전 불일치로 인해 운영 중인 일부 애플리케이션에서 기능이 정상 동작하지 않는 버그가 발생하였다. 하나의 라이브러리를 4개의 앱에서 사용하고 있었는데, 선언은 앱마다 흩어져 있고 버전 표기도 제각각이다. 이 상황에서 내 고민은 2가지로 귀결되었다. 각 패키지의 버전을 **어디에 선언할 것인가**, 그리고 **어떤 버전으로 관리할 것인가**.

이 글에서 이야기 하는 환경은 pnpm 을 사용한다는 가정 하에 작성하지만, 대부분의 내용은 npm·yarn workspace에도 그대로 적용할 수 있다. pnpm 고유라고 부를 만한 건 뒤에 나올 `pnpm.overrides` 정도다.

> 시리즈로 이어진다. 이번 1편은 "어디에 / 어떤 버전으로"라는 선언과 고정의 문제를 다루고, 다음 2편에서는 빌드는 통과하는데도 선언과 실제 사용이 어긋나 있던 의존성들을 다룰 예정이다.

## 1. 먼저, lockfile은 타협 없이 커밋한다

버전 관리 얘기를 꺼내면 보통 `^1.2.3`이냐 `1.2.3`이냐로 곧장 넘어가는데, 그 전에 깔고 가야 할 게 lockfile이다.

`pnpm i`로 패키지를 설치하면 기본적으로 lockfile에 적힌 버전이 그대로 깔린다. package.json에 `^6.30.0`처럼 range로 적혀 있어도, lockfile만 커밋돼 있으면 평소처럼 `pnpm i`로 설치해도 버전은 재현된다. 설치할 때 버전을 정하는 기준이 package.json의 range가 아니라 lockfile이라, 이미 박힌 버전이 range를 만족하는 한 더 새 버전이 나와도 다시 해석하지 않기 때문이다. (range를 다시 풀어 최신으로 올리는 건 `pnpm update`를 명시적으로 실행할 때뿐이다.) 

특히 중요한 건 간접(transitive) 의존성이다. package.json에는 내가 직접 쓰는 것만, 그것도 range로 적힌다. 그게 줄줄이 끌고 오는 수십 개의 간접 의존성을 고정하는 곳은 lockfile밖에 없다. 그래서 직접 의존성을 exact로 박아도 lockfile이 없으면 간접 의존성은 여전히 표류한다.

lockfile을 커밋하지 않으면 사람마다, 설치 시점마다 "그 시점의 range 내 최신"으로 제각각 풀린다. 1월에 설치한 나와 6월에 clone한 동료의 의존성 트리가 달라지는 것이다. 늘 사고로 이어지진 않지만(대개 semver 덕에 넘어간다), 메인테이너의 회귀나 타입 변경, 간접 의존성 표류 때문에 "내 노트북에선 되는데" 식의 버그가 터질 수 있다. 코드 변경이 없으니 원인 찾기도 고약하고, 로컬과 CI·운영 사이에서 갈리면 더 위험하다.

그래서 lockfile 커밋은 논쟁거리가 아니다. 무조건 하는 게 좋다.

## 2. 어디에 선언하나 — 루트 hoist, 그리고 peer/dev/dep

### 루트에 몰아두면 편하지만

모노레포에서 가장 흔한 유혹은 자주 쓰는 라이브러리를 루트 `package.json`에 몰아두는 것이다.

```json
// 개선 전 루트 package.json
"dependencies": {
  "react-router-dom": "^6.28.0",
  "styled-components": "^6.1.1",
  "axios": "1.12.0"
  // ... 총 21개
}
```

루트 `dependencies`는 워크스페이스 전체로 hoisting된다. 그래서 각 앱이 `styled-components`를 자기 `package.json`에 선언하지 않아도, 루트에 있다는 이유만으로 import가 그냥 된다. 당장은 편하지만 이 편의가 곧 부채가 된다. 코드는 선언하지 않은 패키지에 의존하게 되는데, 이걸 보통 <strong>유령 의존성(phantom dependency)</strong>이라 부른다.

이 부채는 3가지 문제를 낳는다.

- 출처를 추적하기 어렵다. 앱의 `package.json`만 봐서는 그 앱이 뭘 쓰는지 알 수 없고, 루트를 봐도 누가 쓰는지는 나오지 않는다.
- 독립성이 깨진다. 루트 의존성 하나만 바꿔도 모든 앱이 영향을 받고, Turborepo 같은 캐시의 신뢰성도 떨어진다.
- strict 모드로 넘어가는 순간 위험하다. 선언 없이 hoist에 기대던 워크스페이스들이 한꺼번에 빌드에 실패한다.

그래서 루트 `dependencies`를 전부 걷어내고, 실제 쓰는 각 앱·패키지에 직접 선언했다.

```json
// 개선 후 루트 package.json
"dependencies": {},          // 완전 제거
"devDependencies": {
  "eslint": "^7.32.0",
  "eslint-config-custom": "workspace:*",
  "prettier": "^2.5.1",
  "turbo": "^1.8.3"          // 워크스페이스 도구만 유지
}
```

루트에는 워크스페이스 전체를 운영하는 도구(turbo, eslint, prettier)만 남겼다. 런타임 라이브러리는 루트에 있어서는 안 된다.

참고로 이 hoist 안티패턴은 pnpm만의 문제가 아니다. 오히려 모든 의존성을 flat하게 hoisting하는 npm, yarn classic에서 더 흔하다. pnpm은 strict 격리를 지향하는 덕에 이 문제를 비교적 일찍, 빌드 실패라는 형태로 드러내줄 뿐이다.

### 공통 패키지는 peer/dev/dep을 구분한다

선언 위치에서 의외로 자주 틀리는 지점이 또 있다. `packages/hooks`, `packages/providers` 같은 공통 패키지가 `react`, `react-dom`을 `dependencies`에 선언하고 있었다.

`react`나 `styled-components`처럼 **싱글턴이어야 하는 패키지**는 호스트 앱과 같은 인스턴스를 공유해야 한다. 그런데 공통 패키지가 이걸 `dependencies`에 두면, 호스트와 별개의 인스턴스가 설치될 수 있다. `ThemeProvider` 컨텍스트가 안 잡히거나 React 훅이 인스턴스 불일치로 조용히 깨지는, 원인 찾기가 꽤 까다로운 버그로 이어진다.

원칙은 이렇게 정리했다.

| 선언 위치 | 적용 대상 | 이유 |
|---|---|---|
| `peerDependencies` | `react`, `react-dom`, `react-router-dom`, `styled-components` 등 | 호스트 앱과 인스턴스 공유 필수 (싱글턴) |
| `devDependencies` | peer와 동일 패키지 | 패키지 자체 로컬 개발·빌드용 |
| `dependencies` | 외부 UI 라이브러리, workspace 패키지 | 번들에 포함되거나 런타임 전용 |

싱글턴이어야 하는 패키지는 `peer + dev`로, 번들에 들어가는 건 `dependencies`로 둔다. 규칙 자체는 단순한데, 일관되게 지키는 건 생각보다 쉽지 않다.

## 3. 어떤 버전으로 — range vs exact

1절에서 봤듯 재현성은 lockfile이 책임진다. 그러면 package.json을 `^6.30.0`(range)으로 쓰느냐 `6.30.0`(exact)으로 쓰느냐는 무엇을 가르는가. 한 문장으로 줄이면 **신뢰를 위임하느냐, 통제를 쥐느냐**의 차이다. range는 semver 규약과 메인테이너를 믿고 자동 갱신을 맡기는 쪽이고, exact는 그 자유도를 거둬들여 모든 변경을 명시적인 액션으로 만드는 쪽이다.

| 항목 | range (`^X.Y.Z`) | exact (`X.Y.Z`) |
|---|---|---|
| 재현성 | lockfile이 보장 | lockfile이 보장 (동일) |
| 변경 가시성 | lockfile diff를 봐야 보임 | package.json diff에 바로 드러남 |
| transitive 자동 갱신 | 일어남 | 막힘 |
| 라이브러리 publish 적합성 | 적합 | 부적합 (호스트 호환 범위 좁힘) |

실무에서 어느 쪽을 쓸지는 대체로 이렇게 갈린다.

- **앱·서비스라면** exact. 버전 결정을 package.json에서 직접 못 박을 수 있어, 버전을 바꿀 때 diff에 바로 드러나고 transitive가 의도치 않게 올라가는 것도 막는다.
- **라이브러리(특히 `peerDependencies`)라면** range. exact로 박으면 그 라이브러리를 쓰는 호스트의 버전 선택을 강제로 좁혀 중복 설치·버전 충돌을 부른다.

다만 exact도 완벽하진 않다. 고정만 해두고 방치하면 1~2년 뒤 의존성이 옛 버전에 묶여 보안 패치도 못 받는다. 그래서 Renovate/Dependabot 같은 갱신 도구가 짝으로 붙는데, 이 얘기는 마치며에서 다시 짚는다.

정리하면 이 프로젝트는 외부에 publish하지 않는 내부 모노레포다. range로 호환 범위를 열어둘 이유가 없으니 전 영역을 exact로 고정했다. 약점인 갱신 정체는 분명히 있지만, 그건 자동 갱신을 붙여 메울 문제이지 exact를 포기할 이유는 아니다(마치며). 한 가지 예외는 있다. 나중에 `packages/*`를 외부에 publish하게 되면, 그 패키지의 `peerDependencies`만은 caret으로 돌려야 한다.

### 단일 진실 공급원: pnpm.overrides

버전 고정에서 모노레포 특유의 문제가 하나 더 있다. 같은 라이브러리가 앱마다 다른 범위로 선언돼 있으면, 실제 설치 버전을 lockfile 없이는 알 수 없다는 점이다.

| 라이브러리 | 앱별 선언 범위 | 실제 설치 버전 |
|---|---|---|
| `react-router-dom` | `^6.4.3` ~ `^6.8.1` 혼재 | 6.30.0 |
| `@types/node` | `^18.0.0` ~ `^20.11.6` 혼재 | 20.17.24 |
| `@types/react` | `^18.0.14` ~ `^18.0.28` 혼재 | 18.3.18 |

선언은 제각각인데 설치 버전은 우연히 하나로 수렴해 있었다. 설계로 보장된 게 아니라 운이 좋았던 거다.

`pnpm.overrides`는 워크스페이스 전체의 의존성 트리에서 특정 패키지의 버전을 **강제로 덮어쓰는** 장치다. 보통의 의존성 선언은 그 패키지 하나에만 영향을 주지만, `overrides`는 내가 직접 선언하지 않은 간접 의존성까지 포함해 트리 어디에 있든 지정한 버전으로 고정한다. 그래서 앱마다 `react-router-dom`을 제각각 선언해뒀어도 여기 한 줄이면 전부 같은 버전으로 수렴한다. 앱마다 버전을 찾아 헤맬 필요 없이, 한 곳만 고치면 워크스페이스 전체가 따라오는 '단일 진실 공급원'이 되는 셈이다.

```json
"pnpm": {
  "overrides": {
    "react-router-dom": "6.30.0",
    "@types/react": "18.0.28",
    "@types/react-dom": "18.0.11",
    "@types/node": "18.16.0"
  }
}
```

다만 `overrides`는 다른 패키지가 요구하는 범위까지 무시하고 덮어쓰기 때문에, 호환되지 않는 버전을 강제하면 오히려 런타임에 깨질 수 있다. 그래서 버전은 임의로 고르지 않았다. `react-router-dom`은 내부 라우팅 코어인 `@remix-run/router`에 의존하는데, 마침 override로 함께 고정돼 있던 `1.23.2`가 `6.30.0`과 짝이 맞는 버전이라 문제가 없었다. 만약 `@remix-run/router`가 `6.30.0`과 호환되지 않는 버전에 묶여 있었다면, 앞서 말한 '범위를 무시한 덮어쓰기'가 그대로 런타임 사고로 이어졌을 것이다. `@types/node 18.16.0`도 `engines.node`·`.nvmrc`·`packageManager`와 그대로 일치하는 값으로 골랐다. "최신이라서"가 아니라 이미 고정돼 있던 것과 아귀가 맞아서 고른 값이다.

npm에는 `overrides`, yarn에는 `resolutions`라는 비슷한 장치가 있다. 도구는 달라도 "버전 결정을 한 곳에 모은다"는 발상은 같다.

`overrides`는 강력한 만큼 상시 정책이라기보다 **목적이 분명할 때 쓰는 국소·임시 도구**에 가깝다. 잘 맞는 상황은 대략 이렇다.

- **보안 패치** — 간접 의존성에 취약점이 있는데 상위 패키지가 아직 안 고쳤을 때, 그 버전만 패치된 것으로 강제.
- **중복 제거** — 같은 라이브러리가 여러 버전으로 깔릴 때 하나로 모아 번들 비대·싱글턴 깨짐을 막을 때.
- **깨진 간접 의존성 우회** — 특정 transitive 버전이 깨졌을 때 상위가 고칠 때까지 임시로 정상 버전에 묶어둘 때.
- **마이그레이션 브리지** — 흩어진 버전을 일단 한곳에서 통일해두고, 선언을 점진적으로 정리해 나갈 때.

반대로 '제대로 된 선언을 고치는 일'을 미루는 영구 우회책으로 쓰면, 트리 전체에 조용히 작용하는 탓에 오히려 진짜 문제를 가린다. 그래서 가능하면 한시적으로 두고, 왜 넣었는지 주석으로 남기는 게 좋다.

이 프로젝트도 마찬가지다. 지금은 상용 서비스를 건드리는 작업이라 사이드 이펙트를 막으려고 overrides를 유지하고 있지만, 어디까지나 임시 방편이다. 후속 작업에서 각 패키지가 자기 버전을 제대로 선언하도록 정리하면서 override를 하나씩 걷어낼 예정이다.

## 마치며

글 서두에 했던 2가지 질문에 대한 답변을 요약하면 다음과 같이 할 수 있다. 

- **어디에 선언하나** — 런타임 라이브러리는 루트가 아니라 실제 쓰는 워크스페이스에. 싱글턴이어야 하는 공유 의존성은 `peerDependencies`로.
- **어떤 버전으로** — lockfile은 무조건 커밋. 그 위에서 앱은 exact 고정, 라이브러리는 range. 그리고 버전 결정은 `overrides` 같은 단일 공급원에 모은다.

다만 exact 고정에는 갱신 정체라는 약점이 따라온다. 고정만 해두고 방치하면 의존성이 통째로 옛 버전에 묶인다. 솔직히 이 프로젝트는 아직 자동 갱신을 붙이지 않았고, 그래서 이건 다음 숙제로 남아 있다. 선택지는 대략 이렇다.

- **Renovate / Dependabot 같은 봇으로 갱신 PR을 자동으로 받기.** patch는 자동 머지, minor·major는 리뷰 후 머지처럼 종류별로 강도를 다르게 둘 수 있다.
- 봇이 부담스럽다면 **분기마다 수동으로 의존성 업데이트 스프린트**를 잡기.
- 최소한 **보안 갱신만이라도** Dependabot security update로 켜두기.

어느 쪽이든 핵심은 같다. 고정은 "변경하지 않는다"가 아니라 "변경을 명시적으로 만든다"는 뜻이고, 그 명시적 변경을 누군가 꾸준히 올려주는 절차가 없으면 고정은 그냥 정체의 다른 이름이 된다.

여기까지는 "선언을 어떻게 둘 것인가"의 문제였다. 그런데 선언을 아무리 잘 정리해도, 그 선언이 **실제 사용과 맞는지**는 또 다른 문제다. 빌드는 멀쩡히 통과하는데도 쓰지 않는 패키지가 남아 있거나, 잘못 선언된 채로 굴러가는 경우가 있다. 다음 글에서는 이 모노레포에서 그렇게 빌드 뒤에 조용히 남아 있던 의존성 문제 네 가지를 추적한 이야기를 다룬다.
